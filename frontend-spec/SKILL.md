# Frontend Spec

## 这个 skill 解决什么

给前端代码一套可执行的工程规范与风格规范。重点不是「能跑」，而是**六个月后别人还能读懂、敢改**。

适用：前端 TypeScript、HTML、CSS、目录结构、命名、导入、文件拆分。

不适用：React/Vue/JSX 专属规则、Node.js 后端、构建产物/依赖策略/测试/CI 流程、lint 工具选型。项目已有 lint 或格式化配置时，以项目配置为准。

## 北极星：人类可读

可读的本质是**边界清楚**：文件边界、模块边界、类型边界、类名边界、信任边界。

1. 显式优于隐式；直白优于聪明；一致优于个人偏好。
2. 命名即文档；注释解释 why，不解释 what。
3. 一个文件、一个函数只承担一个变化原因。
4. 先写清楚，再写短；不要为了 DRY 提前抽象。
5. 格式化交给工具；人只决定结构、命名和边界。

## 工作流

1. **识别改动面**：列出这次要改的文件，以及每个文件属于 TS、CSS、HTML 还是工程结构。
2. **读对应 reference**：按下面的 Reference 地图读；涉及多个语言就都读，不读无关的。
3. **先定边界**：能用一句话说出这个文件负责什么、依赖谁、谁依赖它。说不清，就是边界还没定好。
4. **写代码**：红线必须满足；默认规则优先满足；约定规则按项目现状。
5. **自检**：对本次改动的**每个文件**，过「通用红线」+ 对应 reference 顶部的「本域红线」；正文里标了「禁止/必须/不得」的也按红线处理。有不过的，修完再结束。
6. **说明偏离**：破了红线，在代码注释和最终回复里说明原因；破了默认规则，在最终回复里说明理由。

## 通用红线

跨语言、任何前端文件都适用：

- 一个文件只承担一个变化原因；出现「and」式文件说明该拆。
- 不提交注释掉的代码、未使用的变量/导入、`debugger`、`console.log`。
- 不在代码/注释/HTML 里写密钥、内网地址、个人隐私。
- 文件/目录统一 kebab-case。
- 跨 feature 不直接互相引用；依赖方向遵守 `engineering.md`。
- 不把不可信输入直接插入 DOM 或模板；转义/白名单校验在边界处完成。

语言专属红线在各自 reference 顶部：TS、CSS、HTML、工程结构。

## 规则级别

| 级别 | 含义 | 怎么写 |
| --- | --- | --- |
| 红线 | 违反就是 bug 或一致性事故 | reference 顶部「本域红线」，以及正文里的「禁止/必须/不得」 |
| 默认 | 默认这样做，破例需要理由 | reference 里其余未标注的祈使句 |
| 约定 | 视项目规模/团队约定 | 标了「约定」的条目 |

## Reference 地图

| 文件 | 内容 |
| --- | --- |
| `references/engineering.md` | 目录结构、模块边界、命名、别名、导入顺序、拆文件 |
| `references/typescript.md` | 类型策略、命名、函数、错误处理、注释 |
| `references/css.md` | 原生 CSS、类名约定、token、属性顺序、响应式、a11y |
| `references/html.md` | 文档结构、语义化、表单、a11y、模板、安全 |
| `assets/` | 可选的 EditorConfig / Prettier 基线 |
| `references/provenance.md` | 维护用：与阿里规约、Google 风格指南的取舍记录；写代码时不用读 |

## 最后一条

如果你不确定，选更直白、更少抽象、更容易删除的那个写法。
